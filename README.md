# PS Kalash Steel — B2B Website

Django site for marketing, ad landing pages, admin-managed content and lead capture.

## Run it locally

Python 3.10+ is required by the pinned Django version. The Docker image uses
Python 3.12; the project was also checked in Python 3.14.6.

On Windows PowerShell, from the project directory:

```powershell
.\venv\Scripts\Activate.ps1
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver 127.0.0.1:8000
```

Site: http://127.0.0.1:8000/ — Admin: http://127.0.0.1:8000/admin/

Locally the project uses SQLite and prints emails to the terminal, so no database
or SMTP setup is needed to start. Create Site Settings, categories and products
in the admin; this repository does not contain the `seed_content.py` script
mentioned in an earlier version of these instructions. Django does not read
`.env` files by itself; set environment variables in the shell or hosting
dashboard.

## Fonts

Manrope and Parisienne are **self-hosted** in `static/fonts/` (92 KB total, woff2).
The site makes no request to Google Fonts, which keeps it fast in India and avoids
a third-party dependency on an ad landing page. To change a font, drop the woff2
files in and update the `@font-face` rules at the top of `style.css`.

## SEO and ad tracking

- `/robots.txt` and `/sitemap.xml` are generated by `apps/core/seo.py`.
  `/thank-you/` is excluded from indexing so the conversion page stays out of search.
- Every page sets its own title, meta description, canonical URL and Open Graph
  tags. `static/img/og-image.jpg` is the share image (1200x630).
- The home page carries Organization structured data, product pages carry Product
  structured data.
- Google and Meta tracking IDs are entered in Site Settings. The scripts only
  render when an ID is set, so nothing loads until the client is ready.
- The `generate_lead` and `Lead` conversion events fire once per real submission
  on `/thank-you/`, and not on refresh or a direct visit.

## Images

`static/img/` holds the photos cropped from the client's shop pictures:
`hero-container.jpg`, `product-container.jpg`, `product-bowls.jpg`, `range.jpg`,
plus `logo.png` and `favicon.png` cut out of the logo render. Replace any of
them with better photography when it is available — the product images are
swapped in the admin, the rest by overwriting the file.

## First steps in admin

1. **Site Settings** — fill in phone, WhatsApp, email, address, logo and hero text.
   This one record feeds the header, hero and footer on every page.
2. **Categories** — add at least one (e.g. Containers, Bowls).
3. **Products** — add a product, upload the photo, add specification rows
   (Grade, Sizes, MOQ) and gallery images on the same screen.
   Tick **Featured** to show it on the home page.
4. **Leads** — inquiries land here. Filter by status or campaign, change status
   inline, and export selected rows to CSV.

## Layout

```
apps/core/       site settings, home, static pages, inquiry handling, UTM capture
apps/catalog/    categories, products, gallery images, specifications
templates/       base.html + partials + one file per page
static/          css, js, images (no build step)
media/           uploads (git-ignored)
```

## Lead flow

Ad click with UTM tags → `UTMMiddleware` stores them in the session → visitor
submits any form → `/inquiry/` validates, saves the lead with its source page and
campaign, emails the sales desk → redirect to `/thank-you/`, which fires the
Google and Meta conversion events once per real submission.

Spam is handled by a hidden honeypot field plus server-side phone validation.
No captcha.

## Deploy to Render

Create a **Web Service** from this GitHub repository and select the Python
runtime. Use:

- Build Command: `pip install -r requirements.txt && python manage.py collectstatic --noinput`
- Start Command: `python manage.py migrate && gunicorn ps_kalash.wsgi:application --bind 0.0.0.0:$PORT --workers 2`

Set `DEBUG=0` and a unique, long random `SECRET_KEY`. Render supplies
`RENDER_EXTERNAL_HOSTNAME`, which the project uses for host and CSRF checks.
Configure `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST` and `DB_PORT` for a
managed PostgreSQL database; otherwise Django uses SQLite. Set
`CSRF_TRUSTED_ORIGINS` for any custom domain, for example
`https://www.example.com`. `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`,
`EMAIL_HOST_PASSWORD` and `DEFAULT_FROM_EMAIL` are optional and only needed for
SMTP lead notifications.

The free web service filesystem is ephemeral. SQLite data and admin-uploaded
media stored under `media/` can be lost on redeploy/restart. Use managed
PostgreSQL for database persistence and object storage (for example S3-compatible
storage or Cloudinary) for uploaded media before relying on live leads/uploads.
The app currently uses local filesystem media storage; no cloud media backend is
configured. Static assets are collected and served by WhiteNoise.

After deployment, create an admin user with `python manage.py createsuperuser`
in a Render shell, then add Site Settings, categories and products through
`/admin/`. Run `python manage.py check --deploy` with the production environment
to review Django's deployment checks.

## Verification scripts (optional)

`smoke_test.py` is referenced in older notes but is not present in this repository.

```bash
python manage.py test
```

There are no Django test modules in the repository; `python manage.py test`
currently discovers no tests.

`verify_tracking.js` is an optional browser check, not an automated Django test
suite. It requires Node.js and Playwright (not installed by `requirements.txt`),
a running site and test tracking/product data.

```bash
node verify_tracking.js
```

The verification scripts are development tools, not part of the site.
